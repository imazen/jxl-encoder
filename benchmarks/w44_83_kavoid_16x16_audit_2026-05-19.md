## Verdict

**No double-count.** W44-81 #4 cited "our `find_best_16x16_transform`
re-applies `avoid_transforms_adjust` to the merge candidates per
`ac_strategy_search.rs:2495-2502`" — but those lines are inside
`find_best_32x32_transform_impl` (function starts at line 2262), not
inside `find_best_16x16_transform_impl` (lines 352-884). The W44-81
finding mixed function names.

Both `find_best_16x16` and `find_best_32x32` apply
`avoid_transforms_adjust` **exactly once** per 8x8-class sub-cost:
- In the normal (cached) path: inside `find_best_16x16_transform` during
  the initial 8x8 search, stored into `scratch.entropy_estimate`. The
  32x32 fork reads from cache.
- In the cache-miss fallback path: the 32x32 fork re-applies the same
  adjustments to recreate what the 8x8 search would have stored. This is
  also single-application.

Merge candidates (DCT16X*, DCT32X*, DCT64X*) NEVER receive
`avoid_transforms_adjust` in either code path. Matches libjxl exactly.
