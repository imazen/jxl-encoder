# Color metadata correctness (issue 144)

Tracking: [issue 144](https://github.com/imazen/jxl-encoder/issues/144).

## Explicit ICC presence

Part 1 E.2 requires the ICC selector and profile payload to agree. An explicit
`ColorEncoding.want_icc = true` requires an attached profile. Attaching a
profile selects ICC output even when the caller leaves that flag false.
Missing data returns `InvalidInput`; it cannot produce a header promising an
absent ICC stream. This applies before still/animation request dispatch and
in the separate lossless streaming writer. Lossy streaming delegates to the
still request. Legacy methods without a color-encoding override cannot
construct the mismatched selector.

| Entry path | Guard / evidence |
|---|---|
| Still `EncodeRequest` | Shared admission before pixel dispatch |
| Animation request and wrappers | Same ICC contract, separate request admission |
| Lossy streaming | Finishes through the still request; exact bytes with attached ICC |
| Lossless streaming | Its own admission; exact bytes with attached ICC |
| Optional subsampled RGB8 | Same still admission, all three sampling modes checked |
| Raw JPEG transcode | Imports its own profile; no caller color-selector override |
| Planar integer convenience | No caller color-selector override |

The regression begins with strict Libjxl, then exercises all named strategies,
Custom compact-header/smoothing combinations, and both Reference/Experimental
modes. Present-profile controls fully render through jxl-rs and djxl v0.12,
retain the exact Display P3 profile, and match streaming bytes. The selected
profile control uses packed RGB8; it does not qualify every profile class or
pixel layout. The admission guard itself does not inspect samples or layout.
Gray/RGB correspondence and bounded tag-list prediction are covered below.
Full ICC-content validation remains outside these checks.

## Color-description grammar

Part 1 E.2 uses enum coding for every color-space value. XYB has implicit
white-point and transfer fields; Unknown carries the same primaries fields
as RGB. Both field-presence decisions are independent of strategy and the
compact-header permission. The independent envelope parser follows those
same conditions, including the absent XYB transfer bundle.

`color_header_v012.tsv` comes from the unmodified v0.12.0 `a7a9c78`
component writer. It pins RGB/Gray/XYB fields and every ICC-present enum,
including Unknown. The reference writer rejects Unknown without ICC; that
case instead uses an independent fixed E.2 vector and envelope parsing.
The profile fixtures are generated by that same reference CMS. Component
ICC-present controls isolate grammar; they do not assert a one-byte dummy
ICC is a valid profile.

The production probe varies all named strategies, both values of the relevant
Custom compact-header permission, Reference/Experimental, 64x32/259x17,
RGB8/RGB16, packed/strided still requests, streaming and single-frame animation.
Legacy methods without a color-encoding override cannot select these tags.
Gray input normalizes the tag to Gray, and optional subsampled RGB8 refuses
non-RGB descriptions. The ordinary lossy pipeline writes its RGB/Gray output
description; its source-color interpretation is a separate contract.

On every recorded cell, RGB controls fully decode with exact samples in
jxl-rs and djxl. XYB and Unknown payload bytes and TOC entries match their
RGB controls exactly after independent envelope parsing, including complete
file-size accounting. This establishes lossless sample coding independently
of interpretation of the tag. It does not relabel RGB-control output as an
observed XYB/Unknown render.

The original color writer, reintroduced alone into the pinned current closure,
produces XYB and Unknown descriptions both decoders refuse on these cells.
The corrected XYB descriptions render fully in pinned djxl. The pinned jxl-rs
still refuses XYB with `InvalidColorEncoding`, and both pinned decoders refuse
Unknown without ICC. That is a decoder-support limit, not evidence against
valid syntax. No sibling or reference implementation is modified. Primary
Rust rendering of those descriptions remains unavailable. Admission and color
interpretation findings H4/H5 and full ICC-content validation remain open.

## ICC tag-count predictor bound (H8)

Part 1 E.4.4 permits tag-list commands only when the declared tag count obeys
`128 + 12 * count <= output_size`. The predictor now tests that condition in
u64 before its usize arithmetic. It uses the existing opaque tag-list/main
stream when the condition fails. Header prediction and the decoded ICC bytes
remain unchanged; arbitrary byte strings stay encodable. This does not claim
that arbitrary bytes describe a valid color profile.

Owner decision (2026-11-17): preserve raw payload acceptance, including the
established 4,194,305-byte all-0xAB fixture. ICC-content validity stays the
caller's responsibility; selector/model consistency and the codec's command
bounds remain enforced. The raw-codec contract is distinct from asking a CMS
to parse a profile. Pinned v0.12 initializes its encoder with a default CMS.
Fresh public SetICCProfile controls reject both the 132-byte missing-tag input
and the 4,194,305-byte all-0xAB input, with the default CMS and with an explicitly
attached default CMS. Its internal SetICCRaw instead preserves bytes without
parsing. Preserving this crate's approved raw acceptance is therefore an API
difference from that public setter. Valid prediction behavior follows the
reference; unsafe command counts retain the independently required opaque
coding. `icc-raw-policy-oracle2.log` retains the direct public/internal observations.

Raw coding applies after resolving the source/profile pair. Explicit lossy
input canonicalization can replace or remove the original profile alongside
its pixel-format reduction; the derived request then codes the selected
profile. This existing conversion policy is separate from ICC-content
validation and raw predictor/inverse preservation.

The first 8x8 RGB8 lossless strict regression, with a 132-byte payload declaring
one tag, is 84 bytes / SHA256
`6b55342c8a668961f29530056e39bfbcf80918fd7198c10defae9aedeed03afb`
before the correction and 86 bytes / SHA256
`a19cccea6063c60ae312275fef8909c3802acdb8e23c98bb1d91a9cdabffa109`
with opaque coding. The original primary Rust decoder fails with
`InvalidIccStream`; pinned djxl renders it. Unmodified v0.12's predictor and
inverse also accept this bound-violating case, so decoder agreement cannot
serve as the conformance oracle. The regression independently reads the
predicted command preamble and checks the bound.

The corrected stream fully renders through jxl-rs and djxl and returns every
ICC byte in both. Lossless samples are exact. Retained before/after reference
images match pixel-for-pixel for all paired cells in the selected policy and
entry-path matrix. This comparison does not turn the invalid profile contents
into a valid color description. The original test executable's hash was not
captured before it was rebuilt; source identity, stream hashes and full logs
bind the before observation. Verified fixed executables are retained separately.

## Final ICC pair and source model (H7)

Part 1 E.2 couples profile presence to `want_icc` and the Gray tag to a
profile's grayscale model. The v0.12 public encoder API with its CMS accepts
matched RGB/gray profiles and refuses both mismatches; the frozen control is
`scripts/icc_policy_oracle.cc`. Decoders can render mismatched profiles, so
acceptance alone does not establish this invariant.

The private `FileHeader::write_with_icc` checks the final pair before changing
the output writer. All six production emission sites use it: lossless still
and streaming, both animation writers, VarDCT and JPEG coefficients. Direct
precomputed and prequantized entry points also reach the VarDCT writer.
The container header-length helper re-encodes ICC bytes only to locate their
end; it does not construct a new description/profile pair.

Request admission checks the source layout's model. Both streaming encoders
check before input admission and finish; attaching a profile invalidates prior
admission. The wire check remains necessary after canonicalization, which can
replace/remove a profile, and for direct encoder and JPEG callers.
`GRAY` at ICC bytes 16..20 selects grayscale; this is a model check, not a full
ICC validator. Short/arbitrary non-gray payload acceptance and H8's opaque
coding remain intact. Black-channel/CMYK requirements are a separate H10 item.

Two further paths were exposed by the production controls. Canonicalization
retained an explicit ICC flag after removing its source profile. The derived
request now describes its resulting metadata. Lossy grayscale animation had
never set the encoder's grayscale flag; it now advertises Gray consistently
with its still-image counterpart and accepts a matched gray profile.

The failing canonical control was 61 bytes, SHA256
`16416ea3d6d437eab00667914bb67cbc64b3af74b4e2ceb2e2b0ca8e05a2416b`;
jxl-rs reports `AnsChecksumMismatch` and djxl refuses it. Its flag-unset
control renders. RGB/gray profile mismatches reproduce through still,
streaming, animation and raw/parsed JPEG calls. A CLI run with both streaming
flags records 48 empty prior-output files after late model rejection; with
admission checks those same cases retain their original bytes.

| Surface | Selected production controls |
|---|---|
| All offered policies/modes | Four named bundles, Custom compact-header/smoothing combinations and Reference/Experimental; CLI includes all six accepted strategy spellings |
| Source models | Opposite profiles refused for all 26 current input layouts before pixel dispatch; full ICC validation is not claimed |
| Integer paths | RGB/gray, alpha, 8/16-bit still/streaming/animation; matched gray animation at efforts 1/7/8, 64x32 and 259x17 |
| Canonicalization | sRGB and Display P3, RGBA8/16, packed/padded rows, both explicit selector values; selector values produce identical resulting bytes |

| JPEG | Raw/parsed, bare/container, Stop wrappers, efforts 1/7/9; JPEG APIs do not consume named strategy bundles |
| Optional subsampling | All three modes refuse gray profiles on RGB samples; matched-profile rendering retains the H8 controls |

Both decoders fully render supported outputs; lossless source colors and
recovered ICC bytes are checked independently. Float reference output uses
PFM with declared endianness and complete payload checks: djxl's default PAM
writer cannot represent its float input bit-depth selection. These zero-color
float controls establish the metadata route, not arbitrary HDR color fidelity
or alpha precision. No GPU computation or new rate-control policy is claimed.
Existing byte expectations, ignores and quality bounds stay unchanged.

## H4 before evidence and native controls

At `4572d184`, strict still requests serialize invalid white points, degenerate
primary matrices and forbidden direct gamma values. A singular lossy matrix
panics; gamma2.0 reaches a24-bit writer panic. The legal XYZ-basis primary
set separately panics under D65. Under custom D50 it encodes, but current Rust
has maximum original-sample error0.50379306 and native linear-sRGB output
differs from unmodified v0.12 CMS by1.1509478. The failing streams and exact
source/object/profile are retained in `color-admission-before-pixels`; these
are actual decoded observations, not predicted magnitudes. Production repair
and expanded affected-entry coverage are still pending.

`scripts/color_admission_oracle.cc` keeps three observations separate: public
`SetColorEncoding` status, actual AddImageFrame/ProcessOutput status, and the
unmodified CMS matrix/vector routines. Several invalid fields pass the setter
but fail final encoding. Both XYZ-basis whites have finite native matrix/vector
results even though the public setter refuses their zero primary coordinates.
The reference therefore cannot supply a blanket input-admission rule.

`color-admission-native-production.log` passes (rc0/1 second, peak0.13 GiB,
minimum21652 MiB). `color_admission_v012.tsv` retains the two observed XYZ
vector results. Reproduce using `just color-admission-native <v0.12-source>
<v0.12-build> <new-oracle-path>`. The helper refuses a non-v0.12 build and an
existing executable. The initial new Rust harness compile failure is retained;
its corrected runtime and pixel controls both fail before any production change.

The [ICC specification](https://www.color.org/ICC1-V41.pdf) defines the PCS
white separately from the source-to-source white adaptation. These physical
spaces and their numerical bounds must not be conflated during the repair.
